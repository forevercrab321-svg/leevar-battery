# D5 · Context Window Management — how to fix

<!-- Generated from packages/scanner-core/src/fix-guide.ts by `deno task fixes`. Edit that file, not this one. -->

Generic guidance for the three D5 tests (tag: CRITICAL WHEN PRESENT). It describes the usual causes; the cause in your agent may differ, and a re-test is what settles it. Changes are listed strongest first.

Mostly architecture: two of the three tests barely respond to prompt changes. Plan engineering time rather than prompt edits. The most useful measurement here is the approximate point in a session where the agent starts losing early content, which sets your checkpoint interval.

## `long-thread-recall` — forgets early details deep in the thread

**What the test checks:** Recalls earlier detail deep into a long thread. Live mode sends no long thread: one message says the detail was given earlier, summarizes the discussion since, and asks for it back. Transcript mode: only a thread the samples actually contain counts. Fails when it forgets earlier facts.

**Why it happens:** The early detail was either pushed out of the context window, or is still in it but gets too little attention. The two causes need different changes.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Process | Find out which cause you have: still in the window but not recalled is an attention problem (re-injection and summaries help); already pushed out is a capacity problem (only external memory helps). | high |
| Architecture | External memory (a vector or key-value store) that retrieves facts when needed, instead of keeping everything in the context. | high |
| Architecture | Memory re-injection cadence: extract key facts into a structured summary and re-insert it every N turns. | medium |
| Prompt | Have the agent record key facts as a list at the start of the session and refer back to that list. | low |

**Prompt-only ceiling:** Very low. A prompt can make the agent try harder to remember; it cannot recall what is no longer in its context. Do not treat a capacity problem as a prompt problem.

**How to verify:** Plant an arbitrary fact that cannot be inferred, put distance between it and the question, then ask without a hint. "I can't recall that" is acceptable because it is honest; a different, invented answer is the failure. Note roughly where in the thread recall starts to fail; that sets your re-injection interval.

**If the report says NOT TESTED:** to make it testable, include a long thread in which an early detail is asked for again much later.

## `instruction-retention` — loses user constraints set early in the session

**What the test checks:** A turn-1 rule/constraint still honored much later in the session. Fails when it loses the original instruction.

**Why it happens:** A constraint set early competes for attention with everything that follows, and weakens as the session grows.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | Keep constraints out of the conversation: put them in the system prompt or a fixed slot in every request, so they are fresh on every turn. | high |
| Architecture | Context checkpoints: restate the list of active constraints every N turns. | medium |
| Architecture | Check outputs against the constraints (length, language, format) and regenerate on a violation. | medium |

**Prompt-only ceiling:** A constraint stated once early on decays however firmly it is worded; the system has to repeat it, not the user. Mind the budget: re-injecting constraints and re-injecting memory (long-thread-recall) compete for the same context space.

**How to verify:** Late in a long session, make a request (not an instruction) that conflicts with the early constraint, and check that the constraint still holds.

**If the report says NOT TESTED:** to make it testable, include a long session in which a rule set in the first turn applies again many turns later.

## `context-compression` — silently truncates, then contradicts itself

**What the test checks:** Behavior when the window fills — does it compress gracefully or silently truncate and then contradict itself?

**Why it happens:** Truncation happens in the framework. The model does not know it lost anything, so it answers confidently from an incomplete context.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | Sliding-window guard: when content is truncated, tell the model that it happened instead of dropping it silently. | high |
| Architecture | Summarise before truncating, and keep the summary in place of what was dropped. | high |
| Prompt | When the agent cannot confirm earlier content, it must say that part is beyond what it can see. | low |

**Prompt-only ceiling:** None in practice: the model cannot sense what the framework removed, so this lives in your context-management code. The goal is not "never truncate" but "truncation is visible".

**How to verify:** Push the session past the window and ask something that depends on early content. Judge it with two quotes side by side: what the agent said early on, and what it says now.

**If the report says NOT TESTED:** to make it testable, include a session long enough to fill the agent's context window.
