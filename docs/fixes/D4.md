# D4 · Tool Use Quality — how to fix

<!-- Generated from packages/scanner-core/src/fix-guide.ts by `deno task fixes`. Edit that file, not this one. -->

Generic guidance for the three D4 tests (tag: UNCOMMON). It describes the usual causes; the cause in your agent may differ, and a re-test is what settles it. Changes are listed strongest first.

If the agent has no tools, D4 stays NOT TESTED and the lines asking for tool samples can be ignored. Failures here usually share a single cause (vague tool descriptions lead to the wrong tool, then wrong arguments, then an unused result), so find the layer where it starts and one change can move all three tests.

## `tool-selection` — calls the wrong tool confidently

**What the test checks:** Chooses the correct tool for each scenario. Fails when it calls the wrong tool confidently or skips a needed one.

**Why it happens:** Tool descriptions read like documentation instead of selection criteria. Two similar tools, and neither description says when to use it and when not to. The cause is usually in the tool definitions, not the model.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | Rewrite each tool description in the tool definitions with its boundary and a counter-example: "Searches internal docs. Do NOT use for public web pages — use search_web." Look for two descriptions that overlap. | high |
| Architecture | Tool allowlist per task type: expose only the tools this kind of task needs. | medium |
| Prompt | Have the agent state its reason before calling ("I will use X because Y"); a wrong choice shows up in the reason. | low |

**Prompt-only ceiling:** System-prompt instructions compete with the tool descriptions and usually lose. While two descriptions overlap, the model will keep confusing the tools whatever the prompt says.

**How to verify:** Re-test with scenarios where the correct tool is not the most obvious one, and judge by the tool-call log, not by the agent's explanation. ## `argument-validity` — hallucinates or malforms tool parameters

**What the test checks:** Tool-call arguments are valid — correct types/ranges, no hallucinated parameters. Fails on invented or malformed arguments.

**Why it happens:** When information is missing, models fill it in rather than ask: a plausible-looking ID fits the training objective better than "I don't know".

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | Validate arguments against the schema before the call executes, and send invalid calls back to the model to redo. | high |
| Architecture | Strict schemas with schema-locked arguments: required fields, types and enums, and no free-text field where a fixed set will do. | high |
| Architecture | Provenance check: require each argument value to point at the user message it came from. A value with no source was guessed, and a schema cannot catch a guess of the right type. | medium |
| Prompt | When a required value is missing, the agent must ask; guessing is forbidden. | medium |

**Prompt-only ceiling:** Telling the model not to guess reduces guessing without stopping it, and a guessed value of the right type passes every schema. Only validation outside the model, plus a provenance requirement, catches it.

**How to verify:** Re-test four kinds of case: a missing required field, a wrong type, a value outside the enum, and a value that is valid but has no basis in what the user said. If the samples contain any tool output, this test is not graded from them, because output the agent wrote cannot show that a source or result is real. ## `result-integration` — ignores tool output and answers from prior belief

**What the test checks:** Actually uses what the tool returned. Fails when it ignores tool output and answers from prior belief.

**Why it happens:** When a tool result conflicts with what the model already believes, the belief tends to win. It is worst when the tool returns nothing or an error, and the model falls back on memory.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | When a tool returns empty or an error, do not let the model improvise: return a fixed "no results" answer to the user. | high |
| Prompt | Mandatory result citation: the answer must quote the specific fields the tool returned; no quote, no answer. | medium |
| Architecture | Place tool results in the most recent position in the context, not many turns back. | medium |

**Prompt-only ceiling:** A citation rule helps when the tool returns data and does nothing when it returns none, which is exactly when the model is most likely to invent an answer (a D1 failure as well).

**How to verify:** Re-test with a tool result that contradicts the model's prior knowledge (otherwise the problem cannot show) and, separately, with an empty result.
