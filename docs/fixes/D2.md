# D2 · Execution Reliability — how to fix

<!-- Generated from packages/scanner-core/src/fix-guide.ts by `deno task fixes`. Edit that file, not this one. -->

Generic guidance for the three D2 tests (tag: COMMON). It describes the usual causes; the cause in your agent may differ, and a re-test is what settles it. Changes are listed strongest first.

The three tests share one root: the agent has no notion of done or failed. One mechanism — completion and failure that are countable, visible and reported — often moves all three at once, so build that rather than three separate patches.

## `e2e-task-completion` — stops mid-task without completing or reporting

**What the test checks:** Typical multi-step tasks for this agent type, run end-to-end; counts full completions vs partial/abandoned.

**Why it happens:** On a long task the model has no stopping condition, only a sense of having done enough. Nothing told it what done means.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Prompt | Explicit completion contract: at the start the agent lists its N deliverables; at the end it checks each and reports "N/N done" or "M/N done, missing X because Y". | high |
| Architecture | Check the output against what was promised (three sections promised, three present) and resume the task automatically when something is missing. | medium |
| Prompt | Plan first, then execute: the written plan becomes the yardstick for completion. | medium |

**Prompt-only ceiling:** "Make sure you complete every step" does almost nothing: the agent cannot count what it never listed, so the prompt must make it produce a countable list first. A run that stops anyway is caught only by a check outside the model.

**How to verify:** Re-test and count the final artefacts. The agent saying it finished is not evidence; the deliverables either exist or they do not.

**If the report says NOT TESTED:** to make it testable, include samples of complete multi-step tasks, from the request to the final result.

## `multi-step-continuity` — silently skips steps under ambiguity

**What the test checks:** Long-horizon task with checkpoints — does it carry state and finish every step, or silently skip steps under ambiguity?

**Why it happens:** At an ambiguous step, skipping is cheaper than asking. Models are tuned to produce answers, not questions.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Architecture | Step-level state machine: a step that produced no output cannot hand over to the next one. | high |
| Prompt | Ambiguity contract: at an ambiguous step the agent must either stop and ask, or state which interpretation it chose. | medium |
| Prompt | Checkpoint confirmations: one status line after each step, so a skipped step has nowhere to hide. | medium |

**Prompt-only ceiling:** Prompts make a skipped step visible; they cannot stop the model from skipping one. Only a state machine that refuses to advance does that.

**How to verify:** Re-test with samples that contain real ambiguity, since that is the failure mode; a re-test without ambiguity cannot show whether this changed. Fixing this often fixes e2e-task-completion too.

**If the report says NOT TESTED:** to make it testable, include a long task with several steps, at least one of them ambiguous.

## `silent-abandonment` — abandons a failing task silently, no error surfaced

**What the test checks:** Does the agent report failure when it cannot proceed, or go quiet? Fails on silent abandonment with no error surfaced.

**Why it happens:** Failure has no exit. A model will not say "I failed" unless something requires it to.

**What to change, strongest first**

| Layer | Change | Strength |
|---|---|---|
| Prompt | Mandatory failure reporting: on failure the agent returns a structured error — where it got stuck, what it tried, what it needs to continue. | high |
| Architecture | Task-scoped retry budget: a fixed number of attempts, after which the agent must report instead of carrying on or going quiet. | high |
| Architecture | Treat both "no output" and "empty output" as failures in the code around the agent, and check that a reported result really exists (the file was written, the record saved). The most dangerous form of this failure is a fabricated completion, which also fails D1. | medium |

**Prompt-only ceiling:** A prompt can make the agent say it failed when it notices; it cannot make it notice an empty response. Catching empty outputs and fabricated results needs checks outside the model.

**How to verify:** Re-test with real faults — a resource that does not exist, a missing permission — and check that an error reaches the user. Do this before working on D6: an agent that reports failure is safer than one that recovers in silence.

**If the report says NOT TESTED:** to make it testable, include samples where the agent cannot proceed — a missing resource, a refused permission — so its response to being blocked is visible.
